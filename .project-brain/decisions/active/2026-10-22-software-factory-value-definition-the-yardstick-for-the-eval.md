Owner decision 2026-10-22: this definition of value guides all repository evaluations, architectural comparisons and optimization recommendations for the Software Factory. The campaign rules below apply to the evaluation campaign that starts on 2026-10-22. The owner's verbatim text is support/sources/software-factory-value-definition-2026-10-22.md. Objective: evolve claude_code into a highly capable, reliable, efficient and progressively self-improving Software Factory that can deliver production-ready applications with minimal routine human intervention. Value means measurable improvements in software quality, autonomous execution, delivery efficiency, security, maintainability and intelligent reuse of existing solutions.

Priorities: assess the reference projects against six priorities, weighted as strategic guidance, not rigid scoring rules. Engineering quality 30% (correctness, testing, independent verification, fewer defects, reduced rework); autonomy and orchestration 20% (effective agent coordination, parallel execution, workflow automation, recovery, minimal human intervention); development productivity 15% (faster delivery, shorter feedback loops, reduced engineering effort); security and reliability 15% (safe execution, isolation, permissions, resilience, observability, appropriate approval gates); maintainability and adaptability 10% (architectural simplicity, modularity, reusable capabilities, controlled continuous improvement); resource efficiency 10% (optimized token consumption, model utilization, infrastructure costs, operational overhead). Security and correctness are mandatory acceptance criteria. The campaign reads this as: a capability or recommendation that fails either is not accepted, whatever its other scores.

Reference-driven engineering and intelligent reuse: a fundamental objective is enabling the factory to intelligently leverage existing projects, architectures, skills, agents and implementations rather than unnecessarily reinventing solutions. For every valuable capability identified, determine the best approach: REUSE (adopt an existing compatible component), ADAPT (modify an existing implementation), COMPOSE (combine complementary capabilities), REIMPLEMENT (recreate proven functionality using a more appropriate architecture), BUILD NEW (develop functionality when existing solutions are inadequate), or REFERENCE ONLY / REJECT (preserve useful knowledge or exclude unsuitable approaches). Evaluate these decisions on technical suitability, verified functionality, licensing, security, compatibility, implementation effort, integration risk and long-term maintenance. This decision-making capability should also become part of the factory's standard approach when it develops future applications from supplied reference projects.

Measures: where feasible, establish baselines and assess improvements using first-pass acceptance rate and defect/rework frequency; time from specification to verified delivery; human interventions per successfully completed task; successful autonomous execution and failure recovery; cost and token consumption per accepted deliverable; integration complexity and long-term maintenance burden; effectiveness of reuse versus adaptation or new development. Distinguish demonstrated results from estimates, architectural potential and unverified claims, and implemented capabilities from documented claims.

Direction: prioritize strengthening and connecting the existing capabilities (research, reference repositories, skill and agent adaptation, evaluation, software delivery) rather than introducing redundant systems. Identify what already works, what needs improvement, what is missing, and which external approaches offer demonstrable advantages. Favor native functionality, selective integration, proven engineering patterns, architectural coherence and measurable long-term value. Preserve existing security controls, source provenance, independent verification and human approval for consequential changes. Do not assume that more agents, more automation or greater architectural complexity necessarily create value. Ultimate success criterion: the factory should not merely write code faster; it should intelligently determine the best way to build software, leverage existing solutions whenever appropriate, execute development workflows reliably, and deliver independently verified results with minimal unnecessary human effort and architectural complexity.

Campaign scope: research only; do not implement changes. The output is an evidence-backed optimization strategy with prioritized recommendations for owner approval. The researcher chooses the methodology, evaluation depth, delegation strategy, comparative framework and presentation, prioritizes the most consequential discoveries, avoids unnecessary analysis, and supports important conclusions with evidence. Working rules: (1) until the owner sets a different line, a consequential change is anything that already needs owner approval: push, PRs, merges, branch deletions, skill deploys, and changes under ~/.claude or in GitHub settings. (2) Allowed writes are campaign reports under docs/evaluations/, brain captures, and gitignored eval artifacts under evals/; skills, agents, scripts, hooks and settings are not changed. Evals may run, but skill-eval and agent-eval also write tracked reports (skills/<name>/SKILL-EVAL.md, .claude/agents/<name>-EVAL.md) and, at step 13, hand off to skill-refine or agent-refine when a threshold fails. During the campaign an eval stops at refine-input.json and does not follow that handoff, and its tracked report stays uncommitted unless the owner approves. Refine runs wait for approved recommendations; the first refine then runs one iteration at a time, with the first revert checked by hand (active decision 2026-10-21, PR #4 follow-ups). (3) Coverage of the measures today: first-pass acceptance and defect/rework are approximated by eval pass rate with the analyst pass and by telemetry correction and rejection rates; human interventions per task are approximated by telemetry correction and rejection rates, with no per-task count; autonomous execution is partly covered by agent-eval dispatch accuracy, team-eval Dispatch-Chain Accuracy and Handoff Integrity, and telemetry artifact_production_rate, with no failure-recovery measure; cost and tokens are partly covered by per-scenario total_tokens and duration_ms in timing.json and by the context-footprint metric, with no cost per accepted deliverable; time from specification to verified delivery, integration complexity and maintenance burden, and reuse effectiveness are not measured. Trigger accuracy, project fit and resilience bear on quality and security. The campaign reports what is not measured as estimates and recommends how to measure it. (4) Evals are run fresh against the no-skill or no-agent baseline; reports from before 2026-10-20 are not compared with them (active decision 2026-10-21).

Relation to earlier decisions: two earlier rules stand, reaffirmed by the owner on 2026-10-22. Track A: Hermes proposes improvements and does not develop projects; the human and Claude Code build them (docs/superpowers/specs/2026-07-23-hermes-improvement-proposals-design.md). Track B.1 read-execute runs the Ads audit and report jobs; live mutation (B.2) is parked by D3.2, and code-writing PRs are deferred. D3.2: Hermes holds no write credential for the Google (Ads) accounts and runs read-only against them (canon 2026-09-29-d3-2-decided-hermes-runs-read-only-no-write-credential.md). Its only live write path is the operator-run draft-PR delivery of proposals (Track A Increment 2, infra/hermes-agent/open-proposal-pr.sh), which passes a bot token into the gateway for each delivery run. The Ads mutation tier stays parked: its code is present, but it has no write credential, per D3.2. This definition also does not overrule the approved 2026-10-14 Software Factory architecture evaluation: preserve the current architecture with selective enhancements, reject the two-factory expansion as a new subsystem, and add no autonomous merge path. The AI OS charter (canon 2026-07-17) stands: its north-star is specialized agent teams that coordinate, and the 2026-10-14 evaluation read it as targeting specialized client-service teams, not a general code factory. The new objective (production-ready applications with minimal routine human intervention) is in tension with that reading. This definition is applied within the charter. The owner's aim (2026-10-22) is a factory that can build any kind of app, but the owner chose to let the campaign establish whether becoming a general app-building factory is worth it, so that the decision is well-founded (owner's words: addendum in support/sources/software-factory-value-definition-2026-10-22.md). The campaign therefore assesses that question with evidence, against this definition of value, and brings the owner a recommendation; the charter stays unchanged until the owner decides. Any recommendation that would change Track A, D3.2, the charter or the 2026-10-14 decisions comes to the owner as a separate decision.
