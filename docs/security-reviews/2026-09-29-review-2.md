## Not on the checklist

1. **The D3.2 record contradicts itself.** This is a governance defect in its own right, separate from the verdict. The evidence file says a new dedicated STANDARD write account in Step B and read-only posture with no new account in Step C and findings item 17. A later reader could reinstate a write role on the strength of Step B. *Recommendation:* amend the evidence file so that Step B's line is marked superseded, and keep one authoritative statement. If a write role ever returns, a dedicated STANDARD-access account (spec decision 7) remains my recommendation over ADMIN, and it must never be `hermes@` (F25).
2. **The box holds no read credential, and the findings doc calls `fd18a3b7d0f4` "the box's read credential" (F25).** The sweep reports `credentials: []`, and nothing `.env.ga`-named appears on the box. This is consistent with a read-only posture in which the read audit runs from the laptop. It is also what a sweep that failed to recognise the read credential would show, and F24 showed that sweeps have missed copies before. *Recommendation:* the operator states where the read credential is authorised to live: laptop only, or also the box. If it should be on the box, treat this as a sweep defect (BLOCKING) and find out why the sweep missed it.
3. **The F25 exposure window is unmeasured.** For an unknown period the read account was STANDARD, so the read token (sha12 `fd18a3b7d0f4`) was mutate-capable. *Recommendation:* check the Google Ads change history on the manager and client accounts for any change made by `hermes@` (email sha12 `fa58d3d15139`). No entries means the window can be accepted with evidence. Also find out who raised the level and why, and consider a scheduled laptop run of the access audit (or Google's account-access alerts) so that drift is caught between reviews, not only at them.
4. **The retired ADMIN token is live and unrevoked.** This is accepted as a risk, but the "every copy destroyed" claim rests on sweeps with gaps. The laptop content sweep matched only the `GOOGLE_ADS_REFRESH_TOKEN=` prefix and excluded `~/.Trash` and `~/Library`. A copy in another format (e.g. `google-ads.yaml` `refresh_token:`, a password-manager note, shell scrollback, a chat or AI session transcript) would not match. *Recommendation:* (a) hash every `1//`-shaped string under `~`, including `.Trash`, and look for `b5aa4baf3310`. (b) Confirm that `git log --all -- 'infra/hermes-agent/.env.gaw'` is empty in every clone. (c) State whether the password manager holds it. (d) Close the Hostinger backup and snapshot question (D3.2). The residual risk is permanent while the token stays unrevoked. If the other project's grant can be moved to its own OAuth client, revoking this token becomes safe and removes the risk entirely.
5. **The gateway `.env` now holds a real `ANTHROPIC_API_KEY`.** The findings doc's bring-up recorded a dummy one. The file is `root:root 0600` and the operator states the key is box-dedicated with a workspace spend limit. The gateway container receives it through `env_file`, so a compromised gateway can read it. That is by design, and F19's fix keeps the broker from reading it. *Recommendation:* accept, and record a rotation trigger (any gateway compromise suspicion, and the next review). No Google Ads variables are present (A4), which is consistent with D4.1.
6. **Manual audit runs print raw customer ids.** The D9.1 acceptance reason covers the collector ("discards stderr"). But the evidence file says the operator ran the audit manually and the output was pasted into the assistant session ("Observed: the Google Ads SDK printed raw customer ids to stderr during the audit"). That matches F21's rule that identifiers must not leave the box or laptop in chats. *Recommendation:* run the manual audit with `2>/dev/null` (or through the collector) and scrub before pasting. Confirm that no raw customer id was pasted into the session or any committed file.
7. **Security reviews are published in a public repository.** Repo visibility is accepted in D9.1, but the reason given covers the clone path, not the fact that host layout, findings, and review verdicts, including NOT PASS gaps, are public. *Recommendation:* the operator explicitly accepts publishing review reports publicly, or keeps them out of the public repo.
