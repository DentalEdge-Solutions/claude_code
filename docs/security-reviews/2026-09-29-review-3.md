## Not on the checklist

1. *(Re-judged after operator action.)* **The retired ADMIN grant is still live, with no copy of its token left and no revocation date.** The escrow copy is deleted, so no known copy of the token exists and theft of a stored copy is no longer a live risk. What remains: the grant itself is not revoked, it is ADMIN on a manager account shared with another project, and nobody holds its token any more. So the D8.2 procedure (targeted revoke, then prove death by using the token) can no longer be applied to it. The only remaining route is a grant-level removal on the account, which is exactly the collateral risk the operator is avoiding. **Recommendation:** record an owner for the operator's trigger ("revisit if the other project moves to its own account"). When the other project moves, remove the grant at account level. Also, periodically review the shared ADMIN account's connected-app grants, so an unexpected use of this token would be noticed. *Original item (superseded):* "A live, unrevoked ADMIN refresh token exists off the box" (the password-manager copy), with the recommendation to set a revocation trigger and delete the escrow entry after revoking.
2. *(Re-judged after operator action.)* **The fingerprint's `checklist` component binds to the version string, not the file.** Operator statement: the collector hashes the checklist's version string, and `fingerprint({'checklist': '1.5'})` gives `24c74279…1614`, identical to the bundle's component. That explains the mismatch with the raw file hash (`b606eb83…e733`), and the binding is to v1.5. I accept this on the operator's statement: the collector's code was outside my inputs, so I did not re-derive it. **New consequence:** an edit to CHECKLIST.md that does not bump `version:` leaves the fingerprint unchanged, and so does not re-trigger review. CHECKLIST.md's own header says "Changing this file changes the box fingerprint's `checklist` component", which is not literally true. **Recommendation:** either hash the file bytes, or amend the header to say that only a version bump re-triggers review, and require a bump for every edit (for example with a CI check that the file changed only if `version:` changed). *Original item (superseded):* "could not be tied to the local CHECKLIST.md … the operator confirms that the component was computed from the v1.5 checklist."
3. **The `kind: candidate` value is not defined in checklist v1.5.** D2.1 names only `credential`, `example`, `unparsed` and `unreadable`. The two `candidate` rows (the empty ads `.env` mask target, and the gateway `.env`, which holds a real secret: the dashboard basic-auth password) were judged here from the operator's A4 statement. **Recommendation:** define `candidate` in the checklist, and list the gateway `.env` in the authorised set as a non-Google secret. Then a future sweep that finds a new `candidate` is a mechanical FAIL rather than a judgment call.
4. **The ads app directory holds a `.env` that D6.1 does not report as `extra`.** `/opt/projects/claude-google-ads/.env` (`root:root 0600`, 0 bytes) exists beside an 11-file package whose `extra` list is `[]`. So the package comparison evidently excludes it, presumably as the mask's bind target (F6). It is empty, so there is no exposure. **Recommendation:** state the exclusion in the checklist or the package manifest, so a non-empty `.env` there can never pass D6.1 silently. D2.1 would catch only a Google Ads-shaped value.
5. **Evidence freshness.** (a) Neither bundle carries a collection timestamp. The laptop bundle is reused unchanged from review #2, and the operator's A2 in-memory sweep predates the 14:05 box re-collection. F25 showed that account access can drift within one day. **Recommendation:** have the collectors stamp `collected_at`, fold the in-memory mount sweep into the box collector, and re-run the laptop access audit (D3.1) immediately before operator sign-off, confirming the digest is unchanged. (b) D3.1's row says `declared_role "read (no role declared)"`. Declare the role explicitly in `.env.ga`, so that the mismatch test compares against a stated declaration rather than a default.
6. **The findings doc's header and "Final state" are stale.** They still say the box holds "the operator's deploy key", that the ads repo is a placeholder, and that no units are installed. D6.1/D6.2 and item 16 of the same doc contradict all three. **Recommendation:** update the header so a future reviewer does not read it as a credential that D6.2 missed.
7. **The retired rehearsal client's vault is still on the box.** D5.4 has `retired 1`, and D7.1 lists two vaults. It is `0700` uid 10000, so there is no exposure. **Recommendation:** delete it if nothing needs it, to shrink client data on the box to the one active client.
8. **Minor:** the D2.2 history sweep lists only the two login accounts' `.bash_history`. Consider covering every home's shell and REPL histories (for example `.python_history`, `.zsh_history`, and service accounts' homes). SSH is open to `Anywhere` on 22/tcp. That is within D1.2, but a source restriction (VPN or allow-listed IPs) would cut brute-force exposure further.
