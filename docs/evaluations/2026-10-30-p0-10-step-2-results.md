## 1. Plain-language summary

**What the sitting was.** The owner ran the step-2 runbook in a separate terminal, outside any agent session, in
three parts:
- **Part A**: prove that GitHub refuses the old Hermes bot token `dentaledge-bot-pat`, using the value in the Hermes

**Main results.**

- **`gh` refuses to store a `public_repo` token.** `gh auth login --with-token` answered
  `error validating token: missing required scopes 'repo', 'read:org'`, exit 1. This matches `gh` 2.92.0's source:
  the scope check comes before anything is stored (§3.4).
- **The test token is dead, proved by use.** After its deletion, GitHub answered "Bad credentials", HTTP 401
  (§3.4, §5).
- **The owner's own `gh` login is intact** [Ver by the coordinator] (§3.5).

**What this means for step 3** (§8). The real 90-day token cannot be stored with `gh auth login --with-token`, so
step 3 needs another storage mechanism; the owner chooses it. The real token is minted in step 3, when it is stored
(owner choice of 2026-10-30, §2).

**Why `gh` refused, from its source** [Src]:
- `loginRun` (`pkg/cmd/auth/login/login.go:205-208`) calls `shared.HasMinimumScopes` on a `--with-token` token and
  returns `error validating token: …` on failure. Only after that does it look up the user (`:209`) and call
  `authCfg.Login` (`:215`), the step that stores the token.
- `HeaderHasMinimumScopes` (`pkg/cmd/auth/shared/oauth_scopes.go:77-106`) requires `repo`, and one of `read:org`,
  `write:org` or `admin:org`. It reports both as missing for a token whose `X-OAuth-Scopes` is `public_repo` alone.
  The error text is built at `:17-28` ("missing required scopes 'repo', 'read:org'"). The measured message matches
  it word for word.
- `gist` is listed as a minimum in the help text (`login.go:75`) but is not checked by this code. A token that
  reports no scopes at all passes the check (`oauth_scopes.go:78-82`, "assume that it's an integration token").
- So on the refusal path nothing is stored, in the throwaway folder or in the keychain. Had `gh` accepted the token,
  `AuthConfig.Login` would have called `activateUser` (`internal/config/config.go:389`), which first deletes the
  keyring entry `gh:github.com` with an empty user name (`:460-462`). The keyring is not inside `GH_CONFIG_DIR`, so
  that would have touched the owner's active `gh` entry. This is why the runbook ran C4 only after C3 showed exactly
  `public_repo` [Inf from Src].

**Supporting measurements by the coordinator** (runbook drafting, 2026-10-30) [Ver by the coordinator]: GitHub
answers an empty Bearer token with "Bad credentials", HTTP 401, and a request with no `Authorization` header with
"Requires authentication", HTTP 401. That is why every `try` line in the runbook was gated by a shape check: a
"Bad credentials" reply proves a token dead only if a complete, well-formed token was sent.
