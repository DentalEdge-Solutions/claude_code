**How to read an item.** `source` says where the evidence comes from: `box` (the box
bundle, item id as key), `laptop` (the laptop bundle), or `manual` (the operator states it
in the report). `expected` is what a healthy box shows. The reviewer marks each item
`PASS`, `FAIL` or `CANNOT-VERIFY`, quoting the evidence. An item whose evidence is
`could-not-check` is `CANNOT-VERIFY` — never `PASS`. A `could-not-check` value anywhere inside
an item's data is `CANNOT-VERIFY` for that part of the item. Each bundle carries `collected_at` (UTC):
the box bundle must postdate the last change to the box the report relies on, and the laptop
bundle must be from the same day as the sign-off.

## D1 Host exposure

### D1.1 — Only SSH listens publicly
- **source:** box
- **claim:** the only non-loopback listener, TCP or UDP, is SSH.
- **expected:** `listeners` contains `tcp 0.0.0.0:22` and/or `tcp [::]:22`; every other entry starts with `127.` or `[::1]` (e.g. the dashboard's `tcp 127.0.0.1:9119`); no non-loopback UDP listener unless the operator explains it.
- **pass rule:** no other non-loopback address, TCP or UDP.

### D1.2 — The firewall agrees
- **source:** box
- **claim:** `ufw` is active, default-deny inbound, and allows only 22/tcp.
- **expected:** `Status: active`, `Default: deny (incoming)`, a single `22/tcp ALLOW IN` rule (v4 and v6).
- **pass rule:** no other ALLOW IN rule.

### D1.3 — SSH is key-only, no root login
- **source:** box
- **claim:** `sshd -T` refuses passwords and root.
- **expected:** `permitrootlogin no`, `passwordauthentication no`, `kbdinteractiveauthentication no`, `pubkeyauthentication yes`.
- **pass rule:** all four exactly.

### D1.4 — Brute-force and patch hygiene are on
- **source:** box
- **claim:** fail2ban and unattended-upgrades run.
- **expected:** both `active`.
- **pass rule:** both `active`.

### D1.5 — Only expected accounts can log in or sudo
- **source:** box
- **claim:** login shells and sudo membership are exactly the operator's.
- **expected:** login shells: `root` and `hermesops` only; sudo group: `hermesops` only; `sudoers_d` holds only files the operator recognises.
- **pass rule:** any unexplained account is a FAIL.

### D1.6 — No human or deploy account is in the docker group
- **source:** box
- **claim:** `docker` group membership is root-equivalent, so no login account may hold it.
- **expected:** `docker_group_members` is exactly `["hermes-docker-proxy"]` — the proxy service account, which must reach the Docker socket to broker every container create (by design, BRING-UP Phase 6). Neither `hermesops` nor any other login account appears. (v1.4: the 2026-09-29 review failed v1.3's "empty" expectation on this designed member.)
- **pass rule:** any member other than `hermes-docker-proxy` is a FAIL.

## D2 Credential inventory

### D2.1 — The credential sweep finds exactly the authorised set
- **source:** box
- **claim:** a system-wide sweep (not known paths — F24) finds only authorised credentials, each at its stated owner and mode. Under the read-only posture (D3.2, v1.5) the authorised set holds **no** write credential, so any `.env.gaw` other than `.env.gaw.example` is a FAIL. Since v1.8 the authorised Google credential on the box is exactly one **read** credential at `/etc/hermes/.env.ga`, `root:root 0400`, `kind: credential`, `role: read`, whose `refresh_token_sha12` equals the laptop's `.env.ga` (D3.1). Since v1.11 (Option B) the authorised set also holds the **Anthropic key** at `/etc/hermes/.env.anthropic` (used only by the `ads-drafter`, per run) and the **OpenRouter key** in the gateway `.env` (Hermes's own reasoning); the gateway `.env` holds no Anthropic key.
- **expected:** every row has a `kind`. The authorised set on the box is exactly: (1) ONE `credential` row: path `/etc/hermes/.env.ga`, `role: read`, `owner root`, `group root`, `mode 0o400`, and a `refresh_token_sha12` equal to the laptop's `.env.ga` row (D3.1); any other `credential` row is a FAIL; (2) the Anthropic key: path `/etc/hermes/.env.anthropic`, `kind: authorised-other`, `label: anthropic-key`, `owner root`, `group root`, `mode 0o400`, `anthropic_key_state: real` (`dummy` and `missing` mean the audit cannot draft and are a FAIL), `secrets_held: ["anthropic-key"]`, `secrets_not_searchable: []`; (3) the gateway `.env`: path `/opt/projects/claude_code/infra/hermes-agent/.env` (the real path of `/opt/hermes-agent/.env`: `/opt/hermes-agent` is a symlink into the checkout, and the sweep reports real paths), `kind: authorised-other`, `label: gateway-env`, `owner root`, `group root`, `mode 0o600`, `secrets_held` exactly one of: `["openrouter-key"]` (the dashboard is off); `["openrouter-key", "dashboard-password-hash", "dashboard-session-secret"]` or `["openrouter-key", "dashboard-password-hash"]` (the dashboard is on in the form to use since v1.17: `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH`, the password's scrypt hash, written inside single quotes because Docker Compose interpolates `$` in this file, and optionally `HERMES_DASHBOARD_BASIC_AUTH_SECRET`, which signs the dashboard's sessions so that a restart does not end them; BRING-UP Phase 7); or `["openrouter-key", "dashboard-password"]` (the older form, the plaintext `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD`, still accepted, optionally with `dashboard-session-secret` after it). The dashboard is off by default, and the operator states in the report whether it is on, `secrets_not_searchable: []` (the labels in `secrets_held` whose value is shorter than 8 characters: the leak checks and the collector's own output check skip a value that short, so it is held and never looked for) (the collector reads the file's content to classify it and to load the values `secrets_held` names for the leak checks of D2.2, D2.3 and D10.7; the content is never reported. The collector loads those values from the three files directly, before any item runs, so the leak checks look for them whether or not the sweep reached the file. It also reads the gateway's own values of the same names from the running container (D4.1 `secret_env`). D4.1's `openrouter_env_names` shows the key reached the gateway); (4) the Hermes home secrets file: path `/opt/projects/claude_code/infra/hermes-agent/data/.env` (`/opt/data/.env` in the container), `kind: authorised-other`, `label: hermes-home-env`, owner `10000` (the gateway's uid; the collector prints the number when the host has no such user), mode `0o600`, `secrets_held: ["api-server-key"]`, `secrets_not_searchable: []`, `credential_shaped_names: []` (the sorted assignment names in the file, other than `API_SERVER_KEY`, that contain `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL` or `AUTH`: names only, never a value; reported on this row only); Hermes's start-up writes it from its bundled template plus a generated `API_SERVER_KEY` (from v0.21.5), and Hermes loads it over its environment. The bundle's top-level `credentials` is the authorised credential set, and `--credentials-only` prints the same list: the Google rows (`role`, `refresh_token_sha12`, `client_id_sha12`), then one row per non-Google secret installed (`label`, `sha12`): `anthropic-key` and `openrouter-key` each with a `sha12`, `api-server-key` with a `sha12` (a random 64-hex key) when the Hermes home file holds it, and `dashboard-password` with `sha12: null` when a password is set (a password is listed and never fingerprinted). A `credentials` row whose label is not one of those four, or a missing `anthropic-key` or `openrouter-key` row, is a FAIL. When one of the three non-Google secret files is there and cannot be read, `credentials` is `could-not-check` (the reason names the file's label) and lists no row, the Google rows included, and that file's D2.1 row is `unreadable`. A file that holds bytes that are not UTF-8 (reason `undecodable bytes`; its row is `unreadable` too) or two different values for one secret name (reason `duplicate` and the secret's label; its row stays `authorised-other`) is reported the same way, and every value it holds is still read and looked for. The leak counts of D2.2, D2.3 and D10.7 were then taken without the values that could not be read (the values that were read, and the Google values, were still looked for), so D2.1 and those three items are CANNOT-VERIFY, which takes precedence over the pass rule's FAIL for an `unreadable` row; D3.1's box-side comparison then uses the D2.1 `credential` row's `refresh_token_sha12`. `credentials` is also `could-not-check` when the sweep itself failed (the reason then names no label). In either case `--credentials-only` prints nothing and exits 2. `example` rows are templates. `empty` rows are 0 bytes. No row is `unlisted`, `unparsed` or `unreadable`. A leftover rollback backup such as `/opt/hermes-agent/.env.pre-optb2` is an `unlisted` row (shown at its real path, `/opt/projects/claude_code/infra/hermes-agent/.env.pre-optb2`) and a FAIL until it is shredded (BRING-UP part 2 step 5 creates it; step 6 creates `/root/config.yaml.pre-optb2`, which the sweep does not see; step 10 shreds both before evidence collection, and the operator attaches its `ls` output showing both gone). `not_swept`: `/boot`, `/boot/efi` (kernel and bootloader), `/dev` (device nodes) and `/run/lock` (lock files) are pre-explained; the writable in-memory mounts are covered by `memory_sweep`, whose `name_hits`, `content_hits` and `unreadable` are all empty; any other `not_swept` entry must be explained by the operator. `memory_sweep.namespace_handles` lists Docker `nsfs` namespace handles (under `/run`, bind-mounted network and mount namespaces): they are classified and never read, so a non-empty list is explained and never a FAIL. If `memory_sweep` is `could-not-check`, the operator attaches BRING-UP's manual "Sweep the in-memory mounts" output instead. The operator states in the report that the `/etc/hermes/.env.anthropic` key is real (workspace `hermes-box`, monthly spend limit stated); missing that statement is CANNOT-VERIFY. The OpenRouter key's limit is D10.5's statement.
- **pass rule:** an unexpected credential, a mode wider than `0600` for any future write credential, the authorised read row with any owner, group or mode other than `root`, `root`, `0o400`, the `anthropic-key` row with any owner, group or mode other than `root`, `root`, `0o400` or with an `anthropic_key_state` other than `real`, the `gateway-env` row with any owner, group or mode other than `root`, `root`, `0o600`, an `unlisted`/`unparsed`/`unreadable` row not explained (a rollback backup is never explained: it is shredded), any `memory_sweep` `name_hits`, `content_hits` or `unreadable` entry, or an unexplained `not_swept` entry, is a FAIL. A missing `anthropic-key` or `gateway-env` row is a FAIL, and so is a `secrets_held` other than stated above (a missing `anthropic-key` or `openrouter-key`, or a label not listed), and so is a non-empty `secrets_not_searchable` (BRING-UP Phase 7 requires 16 characters or more for the dashboard password: the operator sets a proper value and re-collects before a report is written). A `dashboard-password` or `dashboard-password-hash` entry with no operator statement about the dashboard (on, or off with a password left in the file) is CANNOT-VERIFY. `dashboard-password` together with `dashboard-password-hash` is a FAIL (Hermes uses the plaintext when both are set, so the hash protects nothing: the operator removes the plaintext line and re-collects). A non-empty `credential_shaped_names` on the `hermes-home-env` row is a FAIL (a credential in this file overrides the gateway's own environment). The `hermes-home-env` row with an owner other than `10000` (or the name the host gives uid 10000) or a mode other than `0o600`, or a missing `hermes-home-env` row, is a FAIL.

## D4 Isolation boundaries

### D4.1 — The gateway cannot read credentials, client data or the governance store
- **source:** box
- **claim:** from inside the gateway container, the governance store, every moved client-data path, the app-state tree and every credential file are absent (or an unreadable or empty mask); no Anthropic or Google Ads variable is in its environment; the control path is readable.
- **expected:** in `paths`, every one of these is `absent`: `/opt/governance`, `/var/lib/hermes/governance`, `/opt/hermes-agent/.env.gaw`, `/opt/hermes-agent/.env.ga`, `/etc/hermes/.env.ga`, `/etc/hermes/.env.anthropic`, `/var/lib/hermes/vaults`, `/var/lib/hermes/reports`, `/var/lib/hermes/draft-out`, `/var/lib/hermes/audit-data`, `/var/lib/hermes/app-state`, `/opt/data/vaults`, `/opt/data/reports` and `/opt/data/home/.claude/settings.json`. `/projects/claude_google_ads/.env` is `readable 0` (the empty mask) or `absent`. `/opt/registry/projects.yaml` is `readable <n>` (the control). `anthropic_env_names` is `[]` and `google_ads_env_names` is `[]` (the gateway holds no Anthropic key: it lives only in `/etc/hermes/.env.anthropic`, D2.1). `openrouter_env_names` is exactly `["OPENROUTER_API_KEY"]`. `secret_env` holds one state for each secret the gateway `.env` may hold (`openrouter-key`, `dashboard-password`, `dashboard-password-hash`, `dashboard-session-secret`), read from the running container with `printenv`; a value is never reported. The states are `matches-file` (the container's value is one the collector read from the file), `differs-from-file` (the container holds a value the collector did not read from the file: the file was edited after the gateway started, it holds a line the gateway's loader reads differently from the collector, it is missing or unreadable, or the value reached the container another way), `unset` (the name is not in the container's environment, or is empty) and `could-not-check` (the container could not be asked, or did not answer as `printenv` does). Expected: `openrouter-key` is `matches-file`; each of `dashboard-password`, `dashboard-password-hash` and `dashboard-session-secret` is `matches-file` when the gateway row's `secrets_held` (D2.1) names it, and `unset` when it does not. (`differs-from-file` for `dashboard-password-hash` is what a hash written without single quotes looks like: Compose cut it short on its way to the container, and nobody can sign in with it; F52.) The container's values join the known secrets before any item runs, so the leak checks of D2.2, D2.3 and D10.7 and the collector's own output check look for the value the gateway really holds, and for its trimmed forms (the value without surrounding whitespace, and each line of a value that holds a line break), however the file spells it. (The gateway's side of D10.1's declared credential map is measured here, not by the probe.) `listeners` is the sorted, de-duplicated local ports (decimal) of every socket in state LISTEN in the gateway container's `/proc/net/tcp` and `/proc/net/tcp6` (one `docker exec cat`; no address or other field is reported). Expected: `listeners` is `[]`, or `[9119]` when the dashboard is switched on (the port D1.1 shows on the host's loopback); the API server (`8642`) must not listen: `config.yaml` carries `platforms.api_server.enabled: false`. Docker's embedded DNS resolver listens on `127.0.0.11` on an ephemeral port in every Compose (user-defined) network; it is not counted in `listeners` and is counted in `docker_dns_listeners`, which is `1` (Docker runs one embedded resolver per container network namespace). Every other address, loopback included, is in `listeners`. A kernel without IPv6 has no `/proc/net/tcp6`, so `listeners` is `could-not-check` (CANNOT-VERIFY); the operator then attaches the port list from `/proc/net/tcp` alone.
- **pass rule:** a path that is readable (other than the control and the empty `.env` mask), any Anthropic or Google Ads variable name, an `openrouter_env_names` other than `["OPENROUTER_API_KEY"]`, a `secret_env` state of `differs-from-file`, `unset` where `matches-file` is expected, or `matches-file` where `unset` is expected (the operator corrects the line or recreates the gateway, then re-collects), or a failed control, is a FAIL; a `secret_env` state of `could-not-check` is CANNOT-VERIFY for this item and for the leak counts of D2.2, D2.3 and D10.7; `could-not-check` is CANNOT-VERIFY. Any port in `listeners` other than the expected (`9119`, and only with the dashboard on) is a FAIL, `8642` included (a new upstream default that opens a listener must be decided, not inherited); `listeners` of `could-not-check` is CANNOT-VERIFY. A `docker_dns_listeners` other than `1` needs an operator explanation; unexplained, it is a FAIL (another process can bind 127.0.0.11, which `listeners` does not show).

### D4.2 — The Docker proxy is live
- **source:** box
- **claim:** `hermes-docker-proxy` is active with its reviewed ExecStart, and no drop-in overrides its unit file.
- **expected:** `active` is `active`; `execstart_sha256` equals `last_pass_execstart_sha256`, which the collector was given with `--last-pass-execstart` (the previous PASS report's value, carried in the bundle), so `matches_last_pass` is `true`. `drop_in_paths` is `[]` (the unit's drop-in files, from a separate `systemctl show -p DropInPaths`: a drop-in under `hermes-docker-proxy.service.d/` changes ExecStart with the unit file byte-identical, which D4.3 cannot see). `execstart_argv_sha256` is the sha256 of that line's `argv[]=…` segment alone (`null` when the line has none); it carries no `start_time` or `pid`, so a restart does not change it. It is recorded as the baseline for the NEXT review and has no pass rule in this one. `matches_last_pass: null` means the flag was not given: the operator then states the baseline (the first review that carries it, #6; the previous PASS report's `execstart_sha256` is the baseline and the reviewer compares by hand).
- **pass rule:** inactive is a FAIL. A non-empty `drop_in_paths` is a FAIL (`could-not-check` there is CANNOT-VERIFY). `matches_last_pass` `false` is a FAIL, unless the operator states that, since the last PASS, the proxy was restarted, the box rebooted, or `systemctl daemon-reload` was run, AND D4.3 shows `installed == repo` for the proxy unit AND `drop_in_paths` is `[]`. (`execstart_sha256` covers the whole `systemctl show -p ExecStart` line, which carries the process's `start_time` and `pid`: a restart or reboot changes them, and a `daemon-reload` resets them to `[n/a]` and `0` while the process keeps running, each with the unit file byte-identical. BRING-UP's chat-trigger rollout runs a `daemon-reload` (part 2 step 4). D4.3 shows the unit file unchanged, and the empty `drop_in_paths` shows that nothing overrides it.) After a `daemon-reload` with no restart, the operator's evidence can also carry the reconstruction of BRING-UP "A security review" step 3: the same line with the running process's `ExecMainStartTimestamp` and `MainPID` put back, whose sha256 equals the last PASS value. When it does, the reviewer records that the proxy's command line is the one last reviewed; it supports the statement and does not replace the three conditions. `null` without the operator's stated baseline is CANNOT-VERIFY.

### D4.5 — The listener check is live
- **source:** box
- **claim:** between reviews, a timer measures the gateway container's listening ports every 15 minutes and records the result, so a listener opened by a later Hermes version, or by the gateway itself, is seen without waiting for a review (F50). It records only: it stops nothing.
- **expected:** `timer_active` is `active` and `timer_enabled` is `enabled` (`hermes-listener-check.timer`). `installed_equal_repo` is `true` for `hermes-listener-check.service` and `hermes-listener-check.timer`, and `drop_in_paths` is `[]` for both. `last` is the latest result as the check wrote it (`ts`, `status`, `reason`, `listeners`, `unexpected`, `docker_dns_listeners`: ports, one count, fixed words and a timestamp, never an address): `last.status` is `ok`, `last.listeners` equals D4.1's `listeners` and `last.docker_dns_listeners` equals D4.1's `docker_dns_listeners`, and `last_age_seconds` is under `max_age_seconds` (2700: three missed runs). The two items measure the same thing from two sides: D4.1 runs `cat` inside the gateway container, which the gateway could tamper with (F35); the check asks Docker for the container's init pid and reads `/proc/<pid>/net/tcp` and `tcp6` on the host, running nothing of the container's. Agreement between them is part of this item. `alert_present` is `false` and `alert` is `null`: the check creates an `ALERT` marker at its first `alert` (a port other than `9119`, or a `docker_dns_listeners` other than `1`) and never removes it; only the operator does, with `check-gateway-listeners.py --clear-alert`, which leaves an `alert-cleared` line. `history_counts` counts every recorded run by `status` (`ok`, `alert`, `could-not-check`, `alert-cleared`; `?` for a line that is not the check's), over at most the last 3,000 runs (about a month). `alert_log` covers every alert and every clearing ever recorded, never trimmed: its counts (`alert`, `alert-cleared`, `?`) and the first and last timestamp (`first_ts`, `last_ts`; `null` when the log is empty), so an alert that was cleared months ago is still in view. On a box that never alerted, `alert_log` is `{"alert": 0, "alert-cleared": 0, "?": 0, "first_ts": null, "last_ts": null}`. A stopped gateway is `could-not-check` with the reason `no-gateway`, never an `alert`, so `could-not-check` runs are expected around a gateway restart or recreate.
- **pass rule:** a `timer_active` other than `active`, a `timer_enabled` other than `enabled`, a unit that is not `installed == repo`, or a non-empty `drop_in_paths`, is a FAIL. `last: null` (the check never ran), a `last.status` other than `ok`, or a `last_age_seconds` of `max_age_seconds` or more, is a FAIL (the operator runs `sudo systemctl start hermes-listener-check.service`, reads `sudo show-listener-check`, and re-collects). `alert_present: true`, any `alert`, `alert-cleared` or `?` count in `history_counts`, or an `alert_log` whose `last_ts` is later than the previous review's collection (or any `?` in it), needs the operator's explanation of each event (when, which port, what was done); unexplained, it is a FAIL. ### D10.6 — Hermes may call exactly three tools
- **source:** box
- **claim:** the box's `mcp_servers` configuration is, value for value, the committed one: one server whose `tools.include` is exactly the three audit tools, with an empty `env`; the tool list the gateway itself reports is recorded as information, not as a boundary.
- **expected:** `mcp_block.equals_repo` is `true`, `mcp_block.reason` is `-` and `mcp_block.canonical_sha256` is `f9b57623687ce28730b8dc1e513707bb9b7d13b2ec9072f597d6b8f3b2e52b70`: the `mcp_servers:` block of the box's `data/config.yaml` holds, value for value, the block committed in `infra/hermes-agent/config.yaml.example` (read from the box's checkout). The reviewer reads the committed block in the repo at the fingerprinted commit; the bundle carries no text of either file, because `data/config.yaml` is writable by the gateway (the collector reads it as hostile: no symlink, a regular file only, at most 64 KiB). The gateway rewrites `data/config.yaml` once it runs (layout, quoting and key order may differ from the template), so lines are not compared: the collector parses both blocks with one strict parser (`bin/mcp_config.py`) and compares the values. Mapping key order does not matter, list order does, and types are exact (`360` is not `"360"`, `false` is not `0`); comments and blank lines are not values. The parser reads only the YAML subset those two layouts use (`key:` lines nested by spaces, `- item` lists, `{}`, `[]`, a one-line `[a, b]`; a value is `true` or `false`, a plain integer, a quoted string with no escape, or a plain word) and never guesses: anything else in the block is `unparseable` (a tab in a line's indentation or in a value, an anchor, an alias, a tag, a block scalar, a flow mapping other than `{}`, a nested flow list, an escape, an inline comment, a value continued on the next line, a quoted key, a key with nothing under it, a list item that is not a scalar, a list directly under `mcp_servers:`, a trailing space, more than one space after a colon, a dash or a comma, an integer of more than 18 digits, a word or number a YAML loader would not read as written, as a value or as a key, such as `yes`, `~`, `0360`, `0x10` or `3.5`). The block's lines are its `mcp_servers:` line and every line up to the next top-level key, blank lines and comments included: more than 200 of them, one of them over 2,000 characters, or nesting deeper than 8 levels, is `unparseable`. Those two limits and the tab rule are the block's only: under the other top-level keys a long line or a tab-indented line is not read and is not a refusal. Anywhere in the file, in a comment or under another key too, these characters are `unparseable`: a carriage return (CRLF line ends included), U+0085, U+2028, U+2029, any other control character except the newline and the tab, a byte order mark, a byte that is not UTF-8 and a literal U+FFFD (what such a byte is read as). A known cause of `unparseable` on a file that is otherwise fine: a value, under any key, that holds a raw U+0085 or U+2028 (some YAML writers put them raw inside a quoted value). Every top-level key of the box file must be a plain name (each line that starts at column 0 and is not a comment is `name:`, then a space or the end of the line) and `mcp_servers` must appear exactly once, so a second key in another YAML spelling (quoted, escaped, tagged, anchored, a complex key, a merge key, a second document) is `top_level_not_plain`, not a pass. `name` is `[A-Za-z_][A-Za-z0-9_-]*`. A line that starts with a tab is at column 0, and indented content before the first top-level key is under no plain key: both are `top_level_not_plain`. Known causes of `top_level_not_plain` on a file that is otherwise fine, each a FAIL with that reason until the rule is deliberately widened: a top-level key that holds an indentless block list (`platforms:` then `- name: x` at column 0, the default of common YAML writers), and a top-level key named outside that pattern (`api.base:`, `2fa:`, a quoted `"on":`). `reason` is from a closed set: `-` (equal); `no_block` (no `mcp_servers:` key, or one that holds nothing: no entry under it, or `{}`); `duplicate_key` (a second plain `mcp_servers:` key, or a key repeated in one mapping of the block); `top_level_not_plain`; `unparseable` (the block is outside the subset or over its limits, or the file holds a refused character); `differs` (the box's block parsed and its values are not the committed ones). `canonical_sha256` is the sha256 of the box block's values as canonical JSON (keys sorted, no spaces), `null` when the block did not parse, and the value above is the committed block's: `bin/security-review-checklist.test.py` keeps it equal to `config.yaml.example`'s, so a change to the committed block is a change to this checklist. What is under the other top-level keys is not parsed, and the collector is not the gateway's loader: `equals_repo: true` says that the file's one `mcp_servers:` key holds the committed values, not that the gateway loads the file. From a file its loader rejects, or one where an earlier key's quoted value is left open across the block, a loader gets no top-level `mcp_servers` key: it cannot get a different one from this file. What Hermes does with such a file is not measured here. `tools.include` is defence in depth and the broker is the boundary (it enforces the schema whatever tools the gateway exposes), and `gateway_mcp_list` is the recorded information that would show a missing or an extra server or tool; report a listing that names a server or tool beyond the three under **Not on the checklist**. `gateway_mcp_list` is recorded as information, and is `could-not-check` (withheld: it is the gateway's own text, printed only when the collector knows every value to look for in it) whenever a D4.1 `secret_env` state was not measured (the `hermes mcp list` text, at most 40 lines, each cut to 200 characters, a credential-shaped line shown as `<withheld>`, a line holding a known secret value never emitted (it refuses the whole bundle); `gateway_mcp_list_rc` is its exit code, `null` when no gateway container ran; an empty list with a non-zero code is noted, not judged).
- **pass rule:** `equals_repo` `false` is a FAIL, whatever the `reason` (`no_block`, `duplicate_key`, `top_level_not_plain`, `unparseable`, `differs`); a `canonical_sha256` other than the value above is a FAIL. `could-not-check` (the box's `data/config.yaml` is missing, a symlink, not a regular file or over 64 KiB, or the checkout's `config.yaml.example` cannot be read or has no `mcp_servers:` block the parser reads) is CANNOT-VERIFY.
