**How to read an item.** `source` says where the evidence comes from: `box` (the box
bundle, item id as key), `laptop` (the laptop bundle), or `manual` (the operator states it
in the report). `expected` is what a healthy box shows. The reviewer marks each item
`PASS`, `FAIL` or `CANNOT-VERIFY`, quoting the evidence. An item whose evidence is
`could-not-check` is `CANNOT-VERIFY` — never `PASS`. A `could-not-check` value anywhere inside
an item's data is `CANNOT-VERIFY` for that part of the item. Each bundle carries `collected_at` (UTC):
the box bundle must postdate the last change to the box the report relies on, and the laptop
bundle must be from the same day as the sign-off.

## D1 Host exposure

### D1.1 — Only SSH listens publicly
- **source:** box
- **claim:** the only non-loopback listener, TCP or UDP, is SSH.
- **expected:** `listeners` contains `tcp 0.0.0.0:22` and/or `tcp [::]:22`; every other entry starts with `127.` or `[::1]` (e.g. the dashboard's `tcp 127.0.0.1:9119`); no non-loopback UDP listener unless the operator explains it.
- **pass rule:** no other non-loopback address, TCP or UDP.

### D1.2 — The firewall agrees
- **source:** box
- **claim:** `ufw` is active, default-deny inbound, and allows only 22/tcp.
- **expected:** `Status: active`, `Default: deny (incoming)`, a single `22/tcp ALLOW IN` rule (v4 and v6).
- **pass rule:** no other ALLOW IN rule.

### D1.3 — SSH is key-only, no root login
- **source:** box
- **claim:** `sshd -T` refuses passwords and root.
- **expected:** `permitrootlogin no`, `passwordauthentication no`, `kbdinteractiveauthentication no`, `pubkeyauthentication yes`.
- **pass rule:** all four exactly.

### D1.4 — Brute-force and patch hygiene are on
- **source:** box
- **claim:** fail2ban and unattended-upgrades run.
- **expected:** both `active`.
- **pass rule:** both `active`.

### D1.5 — Only expected accounts can log in or sudo
- **source:** box
- **claim:** login shells and sudo membership are exactly the operator's.
- **expected:** login shells: `root` and `hermesops` only; sudo group: `hermesops` only; `sudoers_d` holds only files the operator recognises.
- **pass rule:** any unexplained account is a FAIL.

### D1.6 — No human or deploy account is in the docker group
- **source:** box
- **claim:** `docker` group membership is root-equivalent, so no login account may hold it.
- **expected:** `docker_group_members` is exactly `["hermes-docker-proxy"]` — the proxy service account, which must reach the Docker socket to broker every container create (by design, BRING-UP Phase 6). Neither `hermesops` nor any other login account appears. (v1.4: the 2026-09-29 review failed v1.3's "empty" expectation on this designed member.)
- **pass rule:** any member other than `hermes-docker-proxy` is a FAIL.

### D1.7 — The accepted SSH keys are the expected ones
- **source:** box
- **claim:** the box accepts exactly the keys the operator names: one administrative key, and one key limited to the laptop's forward to the dashboard (review #8, F57). No other account holds a key, and no global sshd setting accepts a key or a certificate from elsewhere.
- **expected:** `sshd` holds the global `sshd -T` values (a `Match` block's settings are not read, only counted: `match_lines` is the number of `Match` lines in `/etc/ssh/sshd_config` and `/etc/ssh/sshd_config.d/*.conf`, and `include_elsewhere` the number of `Include` lines in those files that name anything other than `/etc/ssh/sshd_config.d/*.conf`; both `0`; the fingerprint's `entry_points` component carries the whole of `sshd -T`): `authorizedkeysfile` is `.ssh/authorized_keys .ssh/authorized_keys2`; `authorizedkeyscommand`, `authorizedprincipalsfile` and `trustedusercakeys` are `none`; `gatewayports` is `no`; `permittunnel` is `no`; `allowtcpforwarding` is `yes` (the forward needs it) and `allowstreamlocalforwarding` is whatever the box shows (the limited key's options are what refuse it, measured in `docs/evaluations/2026-10-07-limited-ssh-key-and-dashboard-password-replacement.md`). `accounts_checked` is the number of `/etc/passwd` lines read: every account, because one with no login shell can still be used for a forward. `files` has one row per key file that exists, each with `path`, `users` (the accounts whose key file it is), `kind`, `owner`, `group`, `mode`, `keys` and `unparsed_lines` (lines that are neither a key, a comment nor blank). A key is its `type`, its `options` (sorted; a value is printed only for a plain program path in `command` and a loopback target in `permitopen` or `permitlisten`, and is `<withheld>` otherwise) and `sha12` (the first 12 hex characters of the sha256 of the key body); the key body and its comment are never in the bundle. A `sha12` is 48 bits: enough to see that a key changed between reviews, not proof against a key made on purpose to collide; the operator's statement of whose each key is carries that. On this box: exactly one row, `path` `/home/hermesops/.ssh/authorized_keys`, `users` `["hermesops"]`, `kind` `file`, `owner` and `group` `hermesops`, `mode` `0o600`, `unparsed_lines` `0`, and exactly two `keys`: one with `options` `[]` (the administrative key) and one whose `options` are exactly `command="/bin/false"`, `permitlisten="127.0.0.1:1"`, `permitopen="127.0.0.1:9119"`, `port-forwarding`, `restrict` (the forward's key, each limit measured in the evaluation named above: no terminal, no command, no file transfer, a local forward to the literal `127.0.0.1:9119` only (the name `localhost` is refused), and a remote forward only to port 1, which an account without privileges cannot bind while `unprivileged_port_start` is above 1). `unprivileged_port_start` is the kernel's `net.ipv4.ip_unprivileged_port_start`, the first port an account without privileges may bind: `1024` (a host's default) or more. The limited key's `permitlisten` rests on it: measured, with the setting at `0` a remote forward to `127.0.0.1:1` opens a listener on the box's loopback, and at `1024` sshd refuses it (`bind [127.0.0.1]:1: Permission denied`). The report header carries each key's `sha12`, and the reviewer compares them with the previous header's (review #9 is the first with this item: there is no earlier header to compare with, and the operator states whose each key is). `daemon_options` holds, from the running daemon's own command line, `listeners` (the sshd listener processes, `1`), `config_file_options` (its `-f` options, `0`) and `setting_options` (its `-o` options, `0`): `sshd -T`, `match_lines` and `include_elsewhere` all read the default configuration, and these three say whether the running daemon uses it.
- **pass rule:** judged in this order. (1) **Not read:** a `kind`, `owner`, `group`, `mode`, `keys` or `unparsed_lines` of `could-not-check`, a `sshd` value of `could-not-check`, or an `unprivileged_port_start` of `could-not-check`, is CANNOT-VERIFY. An `accounts_checked` of `0` is a FAIL: the account list was not read. (2) **The keys:** the row of `hermesops` must hold exactly two keys: exactly ONE whose `options` are `[]` and exactly ONE whose `options` are the limited set above. Two keys of the same set, a third key, a key whose `options` are neither set (a `<withheld>` value included), `unparsed_lines` above `0`, a `kind` other than `file`, a `mode` other than `0o600`, or an `owner` or `group` other than the account, is a FAIL. A row on any other account, or a second row on `hermesops`, is a FAIL unless the operator states whose key it is and why it stays (a key on `root` that login cannot use is such a case: `permitrootlogin no`, D1.3). (3) **The settings:** `authorizedkeyscommand`, `authorizedprincipalsfile` or `trustedusercakeys` other than `none`, `gatewayports` other than `no`, `permittunnel` other than `no`, or an `authorizedkeysfile` other than the one above, is a FAIL. `allowtcpforwarding` must be `yes` or `local` (with `local` the forward works and no key can ask for a remote forward; the operator states when it was set); any other value is a FAIL, because the forward cannot then work and the evidence does not describe the box as it runs. An `unprivileged_port_start` below `1024` is a FAIL (the limited key could then open a listener on the box's loopback port 1). (4) **`Match` blocks:** `sshd` holds the global settings, and a `Match` block could give one account another `AuthorizedKeysFile`, a key command or a CA. `match_lines` and `include_elsewhere` must both be `0`. `could-not-check` is CANNOT-VERIFY. Another number needs the operator's statement of what each block sets, or what each file brought in from elsewhere holds (a `Match` line there is not counted); unexplained, it is a FAIL. (5) **How the daemon was started:** a `config_file_options` or `setting_options` above `0` means the daemon runs settings this item did not read: it needs the operator's statement of the file or the settings and of what they change, and unexplained it is a FAIL whatever `listeners` is; otherwise `listeners` other than `1`, or any `could-not-check` in `daemon_options`, is CANNOT-VERIFY. (6) **Changes:** a `sha12` that differs from the previous report's header, or a key that is new or gone, needs the operator's statement of which key was replaced, added or removed and when; unexplained, it is a FAIL.

### D2.3 — No credential text in the journal
- **source:** box
- **claim:** as D2.2, for EVERY STORED FIELD of every entry `journalctl` shows, as far back as the journal reaches (D2.4 judges how far).
- **expected:** `journal` holds both counts, `0`. `undecodable_characters` is `0`: the number of replacement characters in the journal text: one for each byte, or cut-short sequence of bytes, that was not valid UTF-8, replaced before the search. `scanned_characters` is the size of the text read, every field included (`journalctl -o json --all --no-pager -q`, one call, read entry by entry; `-q` drops the notices that are not entries (`-- No entries --` for a unit that never logged); it does not drop the warning for a damaged file, which was measured on a call with `-q` (record R14), so the stderr rule below still applies; 41,337,888 at 7.9 days on this box, 2026-10-13, about 5.2 million a day; it grows with the retention to about 183 million; the number jumped once, between review #10 and review #11, when the message-only read ended), `entries` and `fields` are how many entries and field values were searched, and `oldest_entry_read` the UTC time of the oldest entry present just after the search, read by a separate call: entries only ever leave the journal, so the search reached at least that far back. The search is given 300 seconds. An entry that is not a JSON object, or a field that journalctl prints as null, makes the whole item `could-not-check`: what was searched is then unknown. A read that ends with anything on stderr (a truncated or damaged archived file that `journalctl` skips with a warning and rc 0; a caller without the right to read the journal), exits other than 0 or times out makes the whole item `could-not-check`, never a count; so does a collection that is not run as root (`the journal is read as root only`: run by another user, `journalctl` shows that user's own entries only, with rc 0 and nothing on stderr; measured, record R14 item 7). A warning on the oldest-entry call makes `oldest_entry_read` `could-not-check` for the same reason.
- **pass rule:** any non-zero count is a FAIL. A `could-not-check` item (the read ended with a warning, without rights, not run as root, or in time-out, with an entry that did not parse or a field printed as null: what it covered is unknown), an `oldest_entry_read` of `null` or `could-not-check`, or a `scanned_characters` of `0` is CANNOT-VERIFY. An `undecodable_characters` above `0` is not a failure by itself (the search still ran over everything else) but the reviewer states it in the report, and a large number (above `100`) is CANNOT-VERIFY unless explained. A PASS covers the entries back to `oldest_entry_read` only; it stands for the 30 days only when D2.4 passes with `reach_days` of at least `30`; when D2.4 passes on the operator's stated date with a shorter journal, the report states the days the search covered. ### D10.6 — Hermes may call exactly six tools
- **source:** box
- **claim:** the box's `mcp_servers` configuration is, value for value, the committed one: two servers, one per chat-triggered job, each with a `tools.include` of exactly its job's three tools and an empty `env`; the tool list the gateway itself reports is recorded as information, not as a boundary.
- **expected:** `mcp_block.equals_repo` is `true`, `mcp_block.reason` is `-` and `mcp_block.canonical_sha256` is `1c4540386a315a1cffc67167a258bbddae517ea50468c2355ca4de070fc9b5c7`: the `mcp_servers:` block of the box's `data/config.yaml` holds, value for value, the block committed in `infra/hermes-agent/config.yaml.example` (read from the box's checkout). The committed block is two servers, each a three-tool `include` with `env: {}`, six tools in all: `ads_audit` (`command: "python3"`, `args: ["/opt/cc-bin/hermes-app-mcp.py", "--app", "ads-audit"]`, `env: {}`, `timeout: 360`) whose `tools` are `include: [ads_audit_run, ads_audit_status, ads_audit_list]`, `resources: false`, `prompts: false`, and `ads_report` (`command: "python3"`, `args: ["/opt/cc-bin/hermes-app-mcp.py", "--app", "ads-report"]`, `env: {}`, `timeout: 360`) whose `tools` are `include: [ads_report_run, ads_report_status, ads_report_list]`, `resources: false`, `prompts: false`. A box whose block holds one of the two servers only is `differs`. The reviewer reads the committed block in the repo at the fingerprinted commit; the bundle carries no text of either file, because `data/config.yaml` is writable by the gateway (the collector reads it as hostile: no symlink, a regular file only, at most 64 KiB). The gateway rewrites `data/config.yaml` once it runs (layout, quoting and key order may differ from the template), so lines are not compared: the collector parses both blocks with one strict parser (`bin/mcp_config.py`) and compares the values. Mapping key order does not matter, list order does, and types are exact (`360` is not `"360"`, `false` is not `0`); comments and blank lines are not values. The parser reads only the YAML subset those two layouts use (`key:` lines nested by spaces, `- item` lists, `{}`, `[]`, a one-line `[a, b]`; a value is `true` or `false`, a plain integer, a quoted string with no escape, or a plain word) and never guesses: anything else in the block is `unparseable` (a tab in a line's indentation or in a value, an anchor, an alias, a tag, a block scalar, a flow mapping other than `{}`, a nested flow list, an escape, an inline comment, a value continued on the next line, a quoted key, a key with nothing under it, a list item that is not a scalar, a list directly under `mcp_servers:`, a trailing space, more than one space after a colon, a dash or a comma, an integer of more than 18 digits, a word or number a YAML loader would not read as written, as a value or as a key, such as `yes`, `~`, `0360`, `0x10` or `3.5`). The block's lines are its `mcp_servers:` line and every line up to the next top-level key, blank lines and comments included: more than 200 of them, one of them over 2,000 characters, or nesting deeper than 8 levels, is `unparseable`. Those two limits and the tab rule are the block's only: under the other top-level keys a long line or a tab-indented line is not read and is not a refusal. Anywhere in the file, in a comment or under another key too, these characters are `unparseable`: a carriage return (CRLF line ends included), U+0085, U+2028, U+2029, any other control character except the newline and the tab, a byte order mark, a byte that is not UTF-8 and a literal U+FFFD (what such a byte is read as). A known cause of `unparseable` on a file that is otherwise fine: a value, under any key, that holds a raw U+0085 or U+2028 (some YAML writers put them raw inside a quoted value). Every top-level key of the box file must be a plain name (each line that starts at column 0 and is not a comment is `name:`, then a space or the end of the line) and `mcp_servers` must appear exactly once, so a second key in another YAML spelling (quoted, escaped, tagged, anchored, a complex key, a merge key, a second document) is `top_level_not_plain`, not a pass. `name` is `[A-Za-z_][A-Za-z0-9_-]*`. A line that starts with a tab is at column 0, and indented content before the first top-level key is under no plain key: both are `top_level_not_plain`. Known causes of `top_level_not_plain` on a file that is otherwise fine, each a FAIL with that reason until the rule is deliberately widened: a top-level key that holds an indentless block list (`platforms:` then `- name: x` at column 0, the default of common YAML writers), and a top-level key named outside that pattern (`api.base:`, `2fa:`, a quoted `"on":`). `reason` is from a closed set: `-` (equal); `no_block` (no `mcp_servers:` key, or one that holds nothing: no entry under it, or `{}`); `duplicate_key` (a second plain `mcp_servers:` key, or a key repeated in one mapping of the block); `top_level_not_plain`; `unparseable` (the block is outside the subset or over its limits, or the file holds a refused character); `differs` (the box's block parsed and its values are not the committed ones). `canonical_sha256` is the sha256 of the box block's values as canonical JSON (keys sorted, no spaces), `null` when the block did not parse, and the value above is the committed block's: `bin/security-review-checklist.test.py` keeps it equal to `config.yaml.example`'s, so a change to the committed block is a change to this checklist. What is under the other top-level keys is not parsed, and the collector is not the gateway's loader: `equals_repo: true` says that the file's one `mcp_servers:` key holds the committed values, not that the gateway loads the file. From a file its loader rejects, or one where an earlier key's quoted value is left open across the block, a loader gets no top-level `mcp_servers` key: it cannot get a different one from this file. What Hermes does with such a file is not measured here. `tools.include` is defence in depth and the broker is the boundary (it enforces the schema whatever tools the gateway exposes), and `gateway_mcp_list` is the recorded information that would show a missing or an extra server or tool; report a listing that names a server or tool beyond the two servers and their six tools under **Not on the checklist**. `gateway_mcp_list` is recorded as information, and is `could-not-check` (withheld: it is the gateway's own text, printed only when the collector knows every value to look for in it) whenever a D4.1 `secret_env` state was not measured (the `hermes mcp list` text, at most 40 lines, each cut to 200 characters, a credential-shaped line shown as `<withheld>`, a line holding a known secret value never emitted (it refuses the whole bundle); `gateway_mcp_list_rc` is its exit code, `null` when no gateway container ran; an empty list with a non-zero code is noted, not judged).
- **pass rule:** `equals_repo` `false` is a FAIL, whatever the `reason` (`no_block`, `duplicate_key`, `top_level_not_plain`, `unparseable`, `differs`); a `canonical_sha256` other than the value above is a FAIL. `could-not-check` (the box's `data/config.yaml` is missing, a symlink, not a regular file or over 64 KiB, or the checkout's `config.yaml.example` cannot be read or has no `mcp_servers:` block the parser reads) is CANNOT-VERIFY.
